# CINEMATCH Constitution

CINEMATCH connects Vietnamese and foreign film-makers with locations, service partners and the
licensing steps in Vietnam, under the Vietnam Film Development Association (VFDA). This constitution
holds the rules every Spec Kit step (`/speckit-specify` … `/speckit-implement`) and every AI agent must
follow. `AGENTS.md` holds the day-to-day working rules; when the two disagree, this file wins.

## Core Principles

### I. The specs are the source of truth (NON-NEGOTIABLE)

- Requirements come only from `docs/prd.md` (scope), `docs/spec/` (Spec Documents, one per module),
  `docs/screens/` (Screen Specs) and `data/` (data model, schema, seed).
- Every feature, task and line of code cites its source as `<MODULE> §<section> <ID>`
  (for example `M3 §5.1 FR-002`, `M4 BR-005`, `SC-35`).
- An agent never invents a requirement. When a source is silent, ambiguous or two sources disagree,
  the agent stops and writes `[NEEDS CLARIFICATION: question — owner]` instead of guessing.
- `docs/spec/`, `docs/screens/*.md` and `data/` are generated by the scripts in `tools/` and
  `data/seed/`. A change is made in the source script and rebuilt, never patched in the output.

### II. Scope discipline

- The MVP is what `docs/prd.md` marks **Must** (13 items, including moderation M10 FR-001/002).
  Should and Could items are built only after every Must passes its acceptance scenarios.
- Segment A (foreign feature film) is the user every Must is designed for; the pilot recruits
  segment C crews first (`docs/prd.md` §2).
- Won't items (`docs/prd.md` §4.4: logistics M6, showcase and reviews M8, classification pre-check
  M9, integration with the state licensing system, online payments, native mobile app) are never
  built in this release, even when they look easy.

### III. The law is cited, never decided by the software

- CINEMATCH gives guidance and checklists; it never states that a project is legally approved.
- A legal rule is active only when it has a citation and a named approver (M2 BR-002).
- Content pre-check findings show the quoted passage and the rule they come from; the final decision
  is always a human one (VFDA officer or the producer).

### IV. Privacy and security by design (NON-NEGOTIABLE)

- No real personal data in the repository. Seed data is synthetic only: example names, the reserved
  phone range `+84 000 000 xxx` and example e-mail domains (checked by `data/seed/seed_rules.py`).
- No secrets (API keys, passwords, tokens) in any file. Secrets live in `.env`, which is git-ignored.
- Access follows the three information layers of an organisation (public, member, private) and the
  project roles. Row-level security enforces them in the database, not only the user interface.
- Every access to a dossier document is logged (`document_access_log`); every change made by VFDA
  staff is logged (`audit_log`).

### V. Test-first, against the acceptance scenarios

- Each user story's acceptance scenarios (Spec Document §3) become automated tests before the code.
- Business rules that the schema can check inside one row are database `CHECK` constraints
  (`data/schema/`); rules that span tables become triggers, policies or service tests, as listed in
  section 7 of each `data/data-model-<MODULE>.md`.
- `python3 data/seed/check_seed.py` and `python3 data/schema/load_check.py` must stay `PASS` on
  every commit; a red check blocks the merge.

## Technology constraints

- Planned stack: Next.js (web) and Supabase (PostgreSQL, authentication, storage, row-level
  security), as assumed in SYS FR-002, SYS BR-004 and M5. It is confirmed or changed only at
  `/speckit-plan`, and any change is recorded in `plan.md` with the reason.
- The data model in `data/` is the contract. A new table or column first goes into the model
  (`tools/dm_model*.py`), then the schema and the seed are rebuilt.
- The interface is bilingual (Vietnamese and English) from the first screen; no text is hard-coded
  in one language only.
- Dependencies are added only when a task in `tasks.md` needs them, with the reason in the commit.

## Development workflow and quality gates

1. Spec Kit order: constitution → specify → clarify → plan → tasks → analyze → implement.
   `/speckit-analyze` must report no CRITICAL issue before `/speckit-implement`.
2. One branch per task (`<member>/<short-topic>`), one pull request per branch, reviewed by a second
   member. Commit messages: `type: summary` (`feat`, `fix`, `docs`, `chore`, `test`).
3. An agent never runs `git push`, `git reset --hard`, `git clean` or deletes files without asking.
4. After each change the agent lists the changed files with a one-line reason each.
5. Each human gate in `data/data-model-<MODULE>.md` section 12 and each `[NEEDS CLARIFICATION]`
   is closed by the named owner, not by an agent.
6. AI use is recorded in `docs/ai-use-log.md`: the prompt's purpose, the tool, what was accepted
   and what a human changed.

## Governance

- This constitution overrides every other practice in the repository. `AGENTS.md`, `CLAUDE.md` and
  `.agents/rules/` must not contradict it.
- An amendment is made by pull request from the owner (Nam), approved by at least one other member,
  with the version raised: MAJOR when a principle is removed or reversed, MINOR when one is added,
  PATCH for wording.
- Every pull request review checks the change against principles I–V.
